KaiTOR Online TOR runtime acceptance contract
Target game: Mount & Blade II Bannerlord 1.3.15.110062
Target mod: The Old Realms 1.3.15
Required TOR modules: TOR_Armory, TOR_Environment, TOR_Core
Required base runtime load order: TOR_Armory -> TOR_Environment -> TOR_Core -> Coop
Optional validated KaiCleave integration: when KaiCleave v1.3.15.31 is installed on the campaign-process host, the launcher validates KaiCleave plus Bannerlord.Harmony v2.4.2.248, inserts Bannerlord.Harmony ahead of Native and uses TOR_Core -> KaiCleave -> Coop (or TOR_Core -> KaiCleave -> KaiTOR_Stability -> Coop when Stability is also installed). The same KaiCleave version must be active on every connecting client because Coop validates community modules exactly in both directions.
KaiCleave Coop authority rule: the /singleplayer /server /coopsave campaign process keeps KaiCleave combat patches passive because Coop battle collision/damage is simulated by per-mission peers. Every battle client keeps KaiCleave combat patches active, but an attack is eligible only when the attacker is that peer's locally-owned registered player Hero. Local ownership is resolved through Coop PlayerManager.TryGetControlledObjectInfo and ControlledObjectInfo.IsControlled. Remote puppets and NPCs fail the owner-local check. If lookup fails, cleave fails closed. In v0.2.1, PlayerOnly=false is intentionally treated as player-only in Coop until NPC AgentRegistry authority support is added.
Optional validated Stability integration: when KaiTOR_Stability v1.3.15.50 is installed on the campaign-process host, the launcher validates it and inserts it after KaiCleave/TOR_Core and before Portrait Fix/Coop. The same KaiTOR_Stability version must be active on every connecting client because Coop validates community modules exactly in both directions.
Optional validated Portrait Fix integration: when KaiTOR_PortraitFix v1.3.15.60 is installed, the launcher validates KaiTORPortraitFix.dll plus Bannerlord.Harmony v2.4.2.248, inserts Bannerlord.Harmony ahead of Native, and loads KaiTOR_PortraitFix after KaiTOR_Stability/KaiCleave/TOR_Core and before Coop. The same KaiTOR_PortraitFix version must be active on every connecting client.
KaiTOR Stability Coop-safe default: gameplay-affecting TOR StatusEffectMissionLogic replacement is disabled while Coop is active; loading/shader telemetry/prestage/cache acceleration remain available.
Kai Shader Cache Redirector is local cache-path infrastructure, not a Bannerlord community module; it does not participate in Coop module-list validation.
Admission limit: 4 simultaneous players
Authoritative campaign process: Bannerlord.exe /singleplayer /server
TOR topology: rendered campaign-process path with peer-owned battle simulation
TOR_Core metadata: DedicatedServerType=none
Native TaleWorlds dedicated/no-render TOR support: NOT CLAIMED
Validated KaiTOR Coop payload: SubModule.xml, Coop.dll, Coop.Core.dll, GameInterface.dll, Missions.dll.
Steam Workshop policy: persistent TOR junctions in the real Bannerlord Modules directory are forbidden. TOR modules and installed Workshop copies of KaiCleave v1.3.15.31, KaiTOR_Stability v1.3.15.50, KaiTOR_PortraitFix v1.3.15.60, and required Bannerlord.Harmony v2.4.2.248 are discovered by Module.Id, staged with temporary junctions only for the KaiTOR invocation, and removed afterward.
Live readiness requires the installed KaiTOR Coop payload to match the validated package byte-for-byte by SHA-256 before launch authorization.
Runtime acceptance requires ordered TOR_Armory + TOR_Environment + TOR_Core + [optional KaiCleave] + [optional KaiTOR_Stability] + [optional KaiTOR_PortraitFix] + Coop load evidence and an explicit campaign-server ready/running marker. If KaiCleave or KaiTOR_PortraitFix is active, Bannerlord.Harmony must precede Native in the module token.
Shared-map acceptance requires four independent persistent controller/Hero/Clan/MobileParty/CharacterObject graphs.
Movement acceptance requires all four authoritative MobileParty instances to move with non-lockstep evidence.
Battle acceptance with KaiCleave requires at least two connected player controllers to land cleave swings in one continuous battle, campaign-server KaiCleave log to remain passive, battle-peer logs to show CoopPeer + active patches, remote puppets to avoid duplicate cleave, NPC cleave to remain disabled with PlayerOnly=true, and post-battle HP/deaths/campaign state to remain synchronized.
Post-battle live acceptance requires one continuous authoritative server session covering in-battle -> post-battle -> moved snapshots, with append-only runtime and command-output evidence.
Game and TOR assemblies are not distributed by KaiTOR Online; use a legal Bannerlord 1.3.15.110062 + TOR 1.3.15 installation.
Steam discovery acceptance: the tester-facing launcher defaults to Public visibility and publishes a display name through KAITOR_SERVER_NAME. KaiTOR's in-game connection screen opens Steam Lobbies first, shows server name, connected players x/4, compact Coop version, password/access and compatibility, and joins through the existing Steam P2P/relay tunnel. Direct IP remains a fallback and does not replace the Steam path.
VPN/NAT rule: Steam Lobby/P2P is the preferred path when the host uses a VPN or is behind NAT/CGNAT. Manual UDP 4200-4201 forwarding is only a direct-IP/fallback requirement; Steam tunnel acceptance still requires a live test with the user's VPN because VPN policy can block Steam Networking.
